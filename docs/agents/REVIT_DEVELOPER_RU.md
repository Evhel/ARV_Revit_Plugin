# Правила разработчика плагинов ARV

## Задача агента

Писать и исправлять команды панели ARV для Revit 2022. Результат — понятный редактируемый проект Visual Studio и, при изменении рабочего кода, собранный комплект для установки. Общаться по-русски, коротко и по делу.

## Перед изменениями

- Прочитай применимые AGENTS.md, README.md, код затронутой команды и связанные записи docs/AUDIT_RU.md. Посмотри git status и сохрани чужие изменения.
- Сначала найди существующую реализацию и общие помощники src/Common. Исправляй причину ошибки минимальным изменением; не переписывай рабочие команды ради архитектуры или оформления.
- Работай в этом репозитории на дисках C: и D:. Исходную папку D:\Prog\Revit и установленные плагины самостоятельно не меняй.
- Уточняй только то, что влияет на результат и не выясняется из кода или задачи. Если расчёт неоднозначен, не придумывай бизнес-правило.

## Совместимость и исходники

- Цель: Revit 2022, .NET Framework 4.8, x64, C# 7.3, Visual Studio 2022. Сохраняй рабочий ARV_Revit_Plugin.sln и все необходимые .cs, .xaml, .csproj и ресурсы.
- Не сдавай исправление только в DLL. Код должен открываться и редактироваться в Visual Studio без ручного восстановления проекта.
- Используй API именно Revit 2022. Сомнительные сигнатуры сверяй с установленной XML-документацией API или официальной документацией Autodesk нужной версии.
- Не добавляй зависимости и новые общие слои без практической необходимости. Ссылки на RevitAPI и RevitAPIUI оставляй с Private=False; библиотеки Autodesk не включай в поставку.
- Вынесенные алгоритмы делай понятными; имена — по смыслу. Комментарии объясняют причину нетривиального решения, а не повторяют код. Пути установки API задавай через RevitApiPath.

## Revit API и изменения модели

- До изменений проверь документ, контекст команды, выбранные элементы, параметры и доступность операции. Пустой выбор и отмена пользователем — нормальные сценарии.
- Вызывай Revit API только в разрешённом контексте. Фоновая задача и поток UI сами по себе такого контекста не дают. Для модельных операций не используй Task.Run; для необходимого немодального окна используй ExternalEvent.
- Изменения модели выполняй в транзакциях. Для пакетной команды заранее определи: операция целиком либо отдельные независимые элементы. Используй SubTransaction там, где нужен откат одного элемента; не оставляй его частичные изменения после ошибки.
- Сообщай об успехе только после подтверждённого Commit. Не подавляй все исключения и предупреждения Revit. В отчёте различай выполненные операции, пропуски и ошибки с понятными причинами.
- Читай параметры с учётом StorageType; строки через AsString. Перед записью проверяй наличие, тип и возможность записи. Не смешивай параметры экземпляра и типа. Для известных системных параметров используй BuiltInParameter.
- Учитывай внутренние единицы Revit и переводи пользовательские значения явно. Проверяй допустимость имён, конфликтующие номера и повторный запуск команды.
- Не меняй шаблоны видов, закрепление, рабочие наборы, геометрию и другие свойства вне задачи. Не снимай ограничения молча, чтобы операция прошла.
- Проверяй допустимость конкретного действия: например, возможность дублирования вида или его размещения на листе. Не полагайся только на общий тип элемента.
- При значимом порядке задавай сортировку явно; порядок коллектора и создания элементов не считается пользовательской сортировкой.

## Согласованные особенности ARV

- Доступность кнопок проекта проверяет наличие документа и его тип. Не используй динамические Document.IsReadOnly/IsModifiable в callback доступности: ранее это делало все команды серыми. Возможность записи проверяй при выполнении команды; переиспользуй RevitSupport.TryProject, когда подходит.
- «Виды на лист»: сохраняй алфавитный порядок по параметру «Имя вида» (BuiltInParameter.VIEW_NAME), действующее сравнение ru-RU без учёта регистра и дополнительный устойчивый порядок при совпадениях.
- В «Чистовой отделке» сохраняй существующие формулы, коэффициенты и группировку, включая повторное увеличение длины плинтуса. Владелец отдельно попросила оставить эту логику до новой задачи.
- Не возвращай команды создания потолков, контейнера семейств и Export Navis без нового запроса пользователя.

- Для всех команд с листами исключай поля бумаги: слева 20 мм, сверху/снизу/справа 5 мм. Используй Common/SheetMargins.cs. Начальные точки и пользовательские отступы измеряй от внутренней рамки. Не считай поля полезной площадью. В «Виды на лист» прежние 50 мм теперь отсчитываются от рамки.

## UI, иконки и кнопки

- Для окон соблюдай ../design/UI_STYLE_RU.md и используй ../design/ArvTheme.xaml как образец. Для иконок — ../design/ICON_STYLE_RU.md и инструкции в src/ARV_Ribbon/Images/AGENTS.md. Сохраняй общий стиль ARV.
- Не меняй формулы под видом улучшения UI. Сохраняй рабочие обработчики, привязки и смысл полей. Стили подключай к собственным окнам, не к глобальным ресурсам процесса Revit.
- Все окна центрируй на мониторе текущего сеанса Revit через общий UiSupport; Owner бери из UIApplication.MainWindowHandle команды. Правила и обработка DPI заданы в UI_STYLE_RU.md; CenterOwner не заменяет центр экрана.
- Каждой кнопке задавай уникальное внутреннее имя, включающее DLL и полный класс команды. Имя одной DLL нельзя использовать для нескольких кнопок. Проверяй уникальность имён при упаковке.
- При добавлении команды согласованно обновляй проект, решение, точный тип IExternalCommand, привязку кнопки к DLL, доступность, ресурсы и упаковку. Не оставляй кнопку, которая ссылается на отсутствующий класс или файл.

## Проверки без запуска Revit

- Проверку команд в Revit пользователь выполняет вручную. Самостоятельно не подключайся к Revit, не запускай его и не добавляй обязательную автоматическую проверку в Revit как условие завершения задачи.
- Проверяй изменения кода, собирай затронутые проекты и итоговое решение. Выполняй подходящие существующие проверки алгоритмов, XAML, метаданных DLL и комплекта файлов, которые работают без запуска Revit. Исправляй ошибки сборки и предупреждения, вызванные изменением.
- Добавляй тест только для существенной логики или воспроизводимой ошибки, если он действительно проверяет поведение. Не создавай тесты ради количества.
- Подготовь короткий список для ручной проверки пользователем: как запустить команду, какие данные выбрать и что должно получиться; добавь относящиеся к задаче сценарии отмены, пустых данных или повторного запуска.
- Различай фактически выполненные проверки и ожидаемое поведение в Revit. Не утверждай, что сборка или отдельная отрисовка окна доказывает работу команды в Revit. Если проверка сборки недоступна, укажи точную причину.

## Сборка и передача

- При изменении рабочего кода используй build.ps1 для готового комплекта dist/Revit2022, ZIP и SHA-256; согласованно обновляй версию выпуска и документацию. Для изменений только правил или документации не пересобирай DLL и не повышай версию.
- При добавлении проекта обновляй ожидаемые количества, список иконок и проверки в build.ps1/tests осмысленно. Не отключай проверки, чтобы сборка стала зелёной.
- В установочном комплекте должны быть нужные DLL, иконки, .addin и инструкция. Исходники остаются в том же репозитории и открываются через решение. Не включай bin/obj, тестовые DLL, модели пользователей, секреты и библиотеки Autodesk.
- Проверяй соответствие кнопок, классов и файлов, содержимое ZIP и контрольные суммы. Инструкция должна содержать точную папку установки и необходимость закрыть Revit перед заменой DLL.
- Установку пользователь выполняет вручную. Не заменяй загруженные DLL и не меняй Addins самостоятельно. Публикуй изменения в GitHub, когда это входит в порученную задачу; не включай чужие изменения.
- В конце коротко сообщи: что изменено, где исходники и архив, какие проверки прошли, что пользователю проверить вручную. Если задача только про правила, дай ссылки на правила и конфигурацию.
